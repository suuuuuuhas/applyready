# Prove the workflow before promising outcomes

## One-sentence pitch

ApplyReady prepares application photos and signatures against sourced requirements, with local correction and a batch report for student support desks.

## Demo: about 30 seconds

1. Open the photo/signature workspace and choose an exact application cycle and upload field.
2. Choose **Try the synthetic demo**. Explain that this is test artwork, not a student's photograph.
3. Show the measured format/byte failures and source link. Click **Fix this image**.
4. Compare before/after dimensions and bytes. Download the real JPEG. Say: "It passed the implemented file checks; the portal and human review still determine acceptance."
5. Briefly show Batch mode, its per-file report and ZIP. Keep FeeSafe outside this main demo.

The recorded GIF is a UI demonstration. It is not a recording of government portal rejection or acceptance.

## Buyer hypothesis — unvalidated

Start with one junior-college application help desk that already prepares photo/signature uploads for multiple students. A batch of one upload field is the unit of work. Test whether the desk spends enough time checking and repeating image preparation to value this tool.

Ask the operator:

- How many applications and upload problems did you handle last week?
- Walk through the last rejected image. What was the actual error and how did you resolve it?
- Which existing tools do you use and how long does the full process take?
- Can you test one batch with us and compare time/errors against your usual workflow?
- Would you use it again? Who decides on paid tools, and what would justify paying?

Do not treat "sounds useful" as demand or invent pricing. A paid desk plan is a hypothesis, not an established business. Potential year-round packs (scholarships, recruitment and other admissions) require independent source review. Competitors can copy JSON rules; reliable maintenance and distribution need to be earned through actual use.

## Small pilot protocol

Target one consenting operator or 15–20 consenting students. Explain the prototype and let them operate their own accounts. Keep the images local and originals intact. Use anonymous participant codes (P01, etc.) in the evidence ledger; do not store names, application numbers or images in the public repo.

Record a baseline using the current preparation method, then the ApplyReady workflow. Measure time for the same task and count actual format/size issues observed. Separate student estimates from timed observations. Record failures and any legibility problems introduced by compression.

For a real acceptance recording, the participant must control the official portal and final submission. Obtain permission before recording; crop or redact identifiers. Preserve the rejection message, selected exact cycle/field, original measured properties, correction, and actual acceptance result. Merely producing a passing JPEG does not establish portal acceptance.

## Three pitch slides

1. **Problem and real observation:** show an authorized, redacted example and measured preparation time. Until collected, label this evidence pending.
2. **Working workflow:** exact target → diagnose → local correction → visual comparison → JPEG / batch report. Show real software, not a mock portal.
3. **Expansion with evidence:** existing Telangana packs + reviewed national 2026 reference packs → future-cycle and recruitment packs only after verification. State the buyer hypothesis and pilot results separately from roadmap.

## Not implemented by design

OCR is deferred: extracting names/DOB from noisy documents requires a separate accuracy evaluation and user confirmation. There is no government login, automatic submission, fee entitlement decision, background image collection or live-photo replacement.
